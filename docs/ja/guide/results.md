# 結果の解読

## 信頼度

各技術には信頼度バッジが付いており、3 つのレベルがあります：

| レベル | 色     | 意味                                                                                                                 |
| ------ | ------ | -------------------------------------------------------------------------------------------------------------------- |
| **高** | 緑     | 強いシグナルにマッチ：グローバル変数（例：`window.React`）・専用 DOM セレクター・明確なリソース URL（例：`/_next/`） |
| **中** | 黄     | 中程度のシグナルにマッチ：レスポンスヘッダーのあいまいマッチ・CSS クラス名プレフィックス・CSS 変数セット             |
| **低** | グレー | 弱いシグナルにマッチ：汎用スクリプトファイル名のフォールバック（例：`*.min.js`）・あいまいな正規表現                 |

「重要」タブではデフォルトで高信頼度の結果のみ表示されます。

## 証拠

カードには最大 4 行の証拠が表示されます。一般的な証拠には DOM マーカー・リソース URL・レスポンスヘッダー・動的読み込み記録などが含まれます。例：

```text
- DOM ノードに React Fiber マーカーが存在する
- リソース URL が unpkg.com/react@18.2.0/umd/react.production.min.js にマッチ
- レスポンスヘッダー X-Powered-By: Next.js
```

誤検知が見つかった場合はまず証拠を確認してください。問題がリソースルール・レスポンスヘッダールール・幅広すぎる DOM / class マッチのどこにあるかが通常わかります。

## ソース

ソースタグは、この結果がどこから検出されたかを示します：

| ソースタグ                    | 由来                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------------- |
| `レスポンスヘッダー`          | メインドキュメントの HTTP レスポンスヘッダー（server / x-powered-by / set-cookie など）           |
| `レスポンスヘッダー · API`    | 現在のページの XHR / fetch リクエストのレスポンスヘッダー                                         |
| `レスポンスヘッダー · iframe` | ネストされた iframe のメインドキュメントのレスポンスヘッダー                                      |
| `動的監視`                    | コンテンツスクリプト + MutationObserver が継続的に収集したリソース / 動的に読み込まれたスクリプト |
| `動的監視 · ページ操作後`     | ユーザー操作後に読み込まれたリソース（ダイアログ・ログイン・決済）                                |
| `WordPress テーマ`            | テーマの style.css ヘッダーから逆推論                                                             |

**任意のソースタグをクリック**すると底部からパネルが開き、**その技術・そのソース**に対応する生の JSON データのサブセットが表示されます。生のレスポンスヘッダー・リソース URL リスト・動的スナップショットが直接確認でき、完全な JSON を検索する必要はありません。

## 並び順

デフォルトの並び順：

1. カテゴリーインデックス（フロントエンドフレームワーク → UI フレームワーク → ビルドランタイム → CDN → ...）
2. 同一カテゴリー内は信頼度の降順（高 → 中 → 低）
3. 同一信頼度内は技術名の localeCompare 順

特定のカテゴリーに切り替えると、そのカテゴリー内のみで並び替えられます。「重要」タブではすべての高信頼度技術を表示し、高信頼度が一つもない場合はすべての技術から信頼度の降順で上位 30 件を表示します。

## 重複のマージ

同一技術が複数のソースで検出された場合（例：React がレスポンスヘッダーと DOM の両方で検出）、重複して表示されません。1 件にマージされ、信頼度は最も強いものが採用され、証拠配列はマージして重複排除され、sources 配列にはすべての検出ソースが列挙されます。

## 検出されないことは使用していないことを意味しない

このツールが検出するのは「**ウェブページがブラウザーに何の手がかりを公開しているか**」です。サイトが：

- SSR 完了後にすべてのランタイムの痕跡を削除している（例：静的にプリレンダリングされた Astro サイト）
- カスタムサーバーヘッダーをすべてクリアしている
- バンドルファイル名をハッシュ化してフレームワークの元のファイル名を含まない

...場合、拡張機能が検出できる内容は非常に少ないか、まったくない可能性があります。これは通常ルールの問題ではなく、ページがブラウザーに十分な手がかりを公開していないためです。

フロントエンドのビルドの手がかりはバックエンドのランタイムと同じではありません。例えばページに `/_next/`・`/_nuxt/` または Vite の成果物がある場合、それはフロントエンドのビルドチェーンを示しているにすぎず、サーバーサイドが Node.js であると直接推論すべきではありません。バックエンドの言語の特定には通常 `Server`・`X-Powered-By`・Cookie 名・フレームワーク固有のレスポンスヘッダーが必要です。

## 修正ボタン

各カードの「検出が不正確な場合はここをクリックして修正」ボタンをクリックすると GitHub Issue が開き、以下の情報が自動入力されます：

- 現在のページ URL
- この検出結果の JSON
- 確認した証拠
- 拡張機能のバージョン番号

説明欄に「何が間違っているか」または「何として検出されるべきか」を記入してください。メンテナーが [`rules/`](https://github.com/setube/stackprism/tree/main/public/rules) 内の対応するルールを調整します。
